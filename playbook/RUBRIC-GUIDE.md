# Rubric 撰写指南:如何为岗位精读层写出能校准的评审标准

kit 不提供现成 rubric——rubric 的力量恰恰来自**你的**真实校准案例,抄别人的没有效力。
本文给出经多轮校准验证的**条款类型学**与**写法纪律**,照此起草并用自己的案例填充锚点。

## 1. rubric 的定位

规则打分层已做粗排;rubric 只负责**规则读不懂的语义判断**:细分场景是否对口、经历是否
真实、履历是否美化。开头就要向 LLM 声明这个分工,并要求"llm_score 独立给出,不要抄规则分;
宁可分歧,不要迎合"。

## 2. 条款类型学(按此起草你的版本)

### A. 方向甄别类(最大杀因,写最多笔墨)
- **细分场景必须对口,关键词沾边没用**。给出你岗位的判断问句:"他做的那个 X,服务什么业务、他在其中构建了什么?"配真实反例(关键词全中但场景不对口的那种)。
- **点名最常见的方向偏移形态**并列显式反例场景清单(每个岗位都有 2-3 种"听着像、其实不是"的高频邻域,把它们写死)。
- **近义领域切割**:名字里带同一个词但实质不同的领域(如"数据产品"之于"训练数据产品"),给判断锚点问句:"他的 X 服务的是 A 还是 B?"
- **使用者 vs 建造者**:用现成平台拼装应用 ≠ 造平台底座。这条最易误杀,**必须配正例锚点**
  (哪些情况看着像使用者其实是建造者——如底座挂在大厂现成平台名下、title 是运营但做的是底座),
  并写明"真有歧义给待定,不要默认往偏移压"。
- **carve-out(口子)**:业务上认可的例外画像写成窄口(N 条缺一不可),防止一票压死团队模型里有位置的候选。

### B. 真实性甄别类
- **自陈美化高发区**:"个人优势/自我评价/系统学习了X/术语堆砌"不算数,只认经历叙述里可验证的产出。
- **前沿工具名不当深度证据**:工具名是美化重灾区(会随时间换一批热词);处置=不豁免罚分、
  评审意见里给面试前置验证问题(框架选型取舍/一手实操细节/技术判断由谁做)。训练侧硬词难以连贯伪装,可作豁免证据。
- **owner vs 执行者(产品岗第一杀因)**:给三个归因链问句——标准/rubric 谁定?PRD/原型谁产出?系统自建还是上游建的?
  配正反例锚点(用面评原文,最有效)。纪律:**看归因链,不数词频**——自陈 owner 词会骗过统计,真 owner 也可能满篇交付词汇。

### C. 履历算术类(LLM 会偷懒不算,必须显式要求)
- **任期日期算术必须做**:近 N 月内 ≥2 段已离职短任职(≤M 月,非实习)→ 显著压分;
  两段全职长期并行(≥12 月)→ 年限不得重复计算。**必须写量化边界和"明确不扣分"的例外**
  (换工作过渡期短暂重叠、在职 side project 属常态)——无边界的负信号会被模型扩大化误伤,这是实测教训。
- **冗长是负信号**:描述总字数阈值取全池分位(如 p95),映射"抽象总结能力弱"。

### D. 先验类
- **近期经验权重更高**(应用层半年一个范式),旧经历撑起来的相关度要点破。
- **技术 builder 画像可越过 title**:无正式产品 title 但经历体现硬深度的,可通过。
- **执行序列 ≠ 产品岗**,除非体现出向体系建设的跃迁。
- **背书不重复计价**:规则层已按核对过的名单算好 pedigree 并计入总分,rubric 要求"以档案字段为准,
  不要自行重判校档、不要再因背书扣分"——LLM 自行判断学校档位会既错又重复计价(实测踩过)。
  pedigree 只影响 verdict 上限(无背书者上限"待定",除非有极强可验证证据)。

## 3. 写法纪律(比条款本身更重要)

1. **每条锚在真实案例上**:校准案例的细节(哪句面评、什么背景、人工怎么判)是条款的效力来源。
   团队内版本可用去标识化描述;对外分发须重写为合成案例——效力会打折,这是公开的真实成本。
2. **负信号必须带量化边界 + 反例**:写"X 是红旗"必须同时写清阈值和"什么情况明确不算"。
3. **易误杀条款必须配正例锚点**:先写抓什么,紧跟着写"别把这些误伤了"。
4. **输出用严格 schema**:application_id/score/direction/verdict/strengths(≤3条,来自可验证经历)/
   red_flags(只列 rubric 列明的信号)/reasoning(第一句给结论与依据;与规则排名分歧大时说明为什么)。
5. **给分基准段**:各分数段的语义写死(80+ 直接约面 / 60-79 有真实经验但有缺口 / 40-59 沾边不对口 / <40 不对口),
   并明确"不要为显得严格用次要瑕疵压分"。

## 4. 校准流程(rubric 是活的)

1. 首轮起草后,拿**已有人工评审结论**的候选跑对齐,逐条分歧归因:是 rubric 缺条款、边界没闭合、还是 LLM 执行力问题。
2. 修订后**定向复审**受影响的人,不做全体重评——**重跑会静默劣化个案**(把原本正确的扣分理由抹掉),
   全体重评后必须过劣化哨兵(见 core/merge_reviews.py)。
3. 每次修订记 changelog(改了哪条、因为哪个案例、方向是紧是松),修正批以 override 注册进合并器。
4. 模型选型实测:方向判断类语义任务对模型档位敏感,换档前拿同批候选做 A/B 改判率评估。
